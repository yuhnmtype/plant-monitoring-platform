## Also confirmed (Huy, 2026-11-14)

1. Line endings: `.gitattributes` sets `eol=lf` for `*.sql` and `*.yaml`, so every checkout has LF and the profile hash and migration checksums are taken over the raw file bytes. Reason: with `core.autocrlf=true` the same file has CRLF on Windows and LF on Linux, and would hash differently.
2. Tests that need an empty or corrupted database run in a throwaway PostgreSQL schema: the test creates it, sets `search_path`, and drops it afterwards. The demo data is never touched.
3. The plant-term test scans every file under `tests/`.
4. A per-state nominal range may leave out states; a state that is left out uses the sensor's `nominal_range`, which stays required.
5. The same profile and seed with a changed profile file (another hash) adds a run; only an identical profile, seed and hash replaces one.
6. `profiles/engine_test_cell/README.md` has existed since M0, while frozen criteria section 9 says `profile1-done` is tagged before any profile 2 file is added. This is recorded as a dated line in the deviations log (criteria section 10) before the tag, and also in the generality report.
7. The M2 decisions on migrations, runs and data quality are recorded in ADR 0007, because ADR 0001 defers the migration approach to M2 and ADR 0002 describes data quality as "constraints plus a checker".
8. `run_id` is a `bigint` generated identity.
9. The same profile, seed and profile hash keeps its `run_id`: a unique constraint on `(profile_id, seed, profile_sha256)`; a rerun deletes the run's child rows and rewrites them in one transaction. Another seed or another hash adds a run.
10. The per-state range key is `nominal_range_by_state: {<state>: [low, high]}` on the sensor, next to `nominal_range`. Followers may use it.
11. A sensor's per-state ranges are stored for every state of the profile (a state the sensor leaves out gets the sensor's `nominal_range`), so a consumer needs one join and no fallback logic.

## Part A, Must (in this order)

Before item 1 starts, a reference is recorded on `main` (4d9790c) for item 4: the demo is run for `water_treatment` with seed 42, and two SHA-256 hashes are computed from the database and written down with the exact queries used:
- readings: every row ordered by `sensor_id, ts`, one line per row as `sensor_id,ts in ISO 8601 UTC,repr(value)`;
- incident schedule: every label ordered by `start_ts`, one line per row as `class_id,incident_type,split,start_ts,end_ts` in ISO 8601 UTC.

1. Migrations. `db/migrations/0001_*.sql` is exactly the M1 schema; later files change it. `db/schema.sql` is removed, so there is one source of truth. The runner applies pending files in order, each in its own transaction, and records version and checksum in `schema_migrations`. It refuses when the checksum of an already applied file has changed, and refuses when tables exist without `schema_migrations`; each refusal names the problem and changes nothing. The demo calls the runner instead of applying `db/schema.sql`. Tests cover each refusal and an idempotent re-run (a second run applies nothing and changes nothing), in a throwaway PostgreSQL schema. `.gitattributes` (`eol=lf` for `*.sql` and `*.yaml`) is added before the first checksum is recorded.
2. Runs. `runs` (run id, profile id and name, `simulated` with a CHECK, seed, SHA-256 of the profile file, sampling interval, `created_at`) replaces `profiles`. `run_splits` (run, split, start, end) stores the split bounds of each run. `sensors`, `readings`, `context_readings` and `incident_labels` are keyed by run. Re-running the same profile, seed and profile hash replaces only that run; another seed, or the same seed with a changed profile file, adds a run. The demo command stays `python -m plantmon demo --profile <id> [--seed N]`, and every query of the demo (chart, row counts) is filtered by the run it just wrote. `test_second_run_replaces_the_first` is replaced by tests for these three behaviours.
3. Optional per-state nominal range per sensor: a profile key on the sensor and a table keyed by run, sensor and state. Reason: frozen criteria section 3 defines R0 as "outside range for the current regime if the profile defines regimes", and ADR 0006 names this consequence. A profile without states is unchanged. A state that a sensor leaves out uses the sensor's `nominal_range`, which stays required. The loader rejects an unknown state and `low >= high`. Tests use neutral names (`alpha`, `beta`).
4. Regression: for seed 42, the stored readings and incident schedule of `water_treatment` are identical before and after Part A. Checked by recomputing the two hashes recorded before item 1 with the same queries, filtered to the new run, and comparing them.
5. Data-quality checks as SQL files under `db/`, run per `run_id`. Results go to `dq_results` (run, check id, passed, violation count, `checked_at`). The demo runs them and exits non-zero when one fails.
   a. Sample count: for each sensor and split, the count equals split length / interval. The two 7-day gaps are expected holes, derived from `run_splits`.
   b. Regular step: consecutive timestamps of one sensor inside a split differ by exactly the interval.
   c. Finite values: no NaN and no positive or negative infinity. PostgreSQL `double precision` accepts all three, so the type alone does not exclude them.
   d. Nothing outside the splits: no reading and no context row lies outside every split of its run.
   e. Labels inside their split: every incident label lies inside the split it names.

   Each check has a test that passes on a clean small run and fails after one deliberate corruption, while the other four checks still pass:
   a. delete the last reading of one sensor in one split;
   b. move one reading inside a split by one minute;
   c. set one value to NaN;
   d. insert one reading at a timestamp inside a gap;
   e. move the end of one label one hour past the end of its split.
6. Indexes. Each index names the query it serves. The first candidate serves "all sensors of one run in a time window": `SELECT sensor_id, ts, value FROM readings WHERE run_id = $1 AND ts >= $2 AND ts < $3`, with a 14-day window as in the demo chart. Raw `EXPLAIN (ANALYZE, BUFFERS)` is pasted before and after, at full size: 314,496 readings per run, with 5 runs loaded (seeds 42-46, P5). If an index does not help, it is not added, and that is reported with the same prominence as one that helps.
7. Plant-term test. Each profile folder gets a `plant_terms.txt`, one term per line. For `water_treatment` this is the M1 grep list minus `engine`: `pump`, `valve`, `tank`, `water`, `flow`, `pressure`, `treatment`. One test reads every such file and fails if any term occurs, case-insensitive, in a file under `src/plantmon/`, `db/` or `tests/`. The test file itself contains no plant term. Terms must be specific enough not to hit generic core words: for example `full_load`, not `load`, which already occurs in `load_profile`. A deliberate failure is shown once, with raw output, and not committed.
8. The missing M1 test: a profile whose `context.schedule.daily_hours` leaves out a state is rejected with "context.schedule.daily_hours must list every state".
9. ADR 0007 records the migration approach, runs and the data-quality approach (SQL checks with results in `dq_results`, no new constraints), and how it relates to ADR 0001 and 0002.
10. A deviations log, `docs/deviations.md`, is started with one dated line: `profiles/engine_test_cell/README.md` has existed since M0, while frozen criteria section 9 says `profile1-done` is tagged before any profile 2 file is added.
11. pytest and ruff pass, with raw output pasted. The README status table is updated only when Part A is done. Then the tag `profile1-done` is created after Huy's "xong".

## Known limits

- Regimes follow a fixed daily clock and only add an offset. The relation between sensors and the noise level do not change with the regime.
- A step offset stands in for "ramp"; there is no gradual transition.
- Migration 0002 drops stored simulated data; it is regenerated from the seed.
- The plant-term test matches substrings, so a term such as `flow` also matches an unrelated word that contains it.
- The profile hash is taken over the raw file bytes, so a change to a comment or whitespace in a profile file also counts as a changed profile and adds a run.
- The regression hashes were recorded on one machine (Windows). A reproduction on Linux with the pinned numpy 2.5.4 gave the same incident-schedule hash but a different readings hash (the first reading is identical). The cause is not known. So "same seed, identical readings" holds on one machine and one set of library versions, and the readings hash in this spec is a same-machine reference only.

## Known consequence

- The migration runner, runs and data-quality checks are core code written before profile 2 exists as a file. The generality diff only covers changes after `profile1-done`; capabilities added before it are listed in the generality report (Part B item 4).

Queries (`<column>` is the filter column, `profile_id` here):

```sql
SELECT sensor_id, ts, value FROM readings WHERE <column> = %s ORDER BY sensor_id COLLATE "C", ts
SELECT class_id, incident_type, split, start_ts, end_ts FROM incident_labels WHERE <column> = %s ORDER BY start_ts
```

Line format: one line per row, UTF-8, each line ends with `\n` (LF), fields joined by `,` with no spaces.

- readings: `sensor_id,ts,repr(value)`, where `repr` is Python's `repr` of the `float` that psycopg returns for `double precision`.
- incident schedule: `class_id,incident_type,split,start_ts,end_ts`.
- Every timestamp is converted in Python with `ts.astimezone(datetime.UTC).isoformat()`, for example `2025-01-01T00:00:00+00:00`.
- `COLLATE "C"` fixes the order of `sensor_id` to byte order, so it does not depend on the database locale.

First readings line: `outlet_flow,2025-01-01T00:00:00+00:00,162.8232616079465`. First schedule line: `sensor_drift,fault,validation,2026-01-10T21:00:00+00:00,2026-01-11T04:15:00+00:00`.
