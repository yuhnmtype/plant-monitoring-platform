## Measured: sigma_s per sensor (RAN, 2026-11-20, simulated data)

Method: profile 1 (`water_treatment`), seeds 42-46 (P5), the reported layer, the training split only (35,040 samples per sensor, 365 days, 96 slots per day). The time-of-day profile of a sensor is the mean of its training values in each time-of-day slot; sigma_s is the sample standard deviation (ddof 1) of the value minus that profile. The measuring script is a throwaway and is not committed; the method above is the specification. In M3a the simulator computes sigma_s itself, per run, from that run's training split before any injection (the training split holds no incidents).

| Sensor | Unit | sigma_s, seed 42 | Min over seeds 42-46 | Max over seeds 42-46 |
|---|---|---|---|---|
| pump_command | percent | 1.0038 | 0.9807 | 1.0038 |
| pump_flow | m3/h | 4.0268 | 4.0003 | 4.0424 |
| pump_pressure | bar | 0.0583 | 0.0578 | 0.0583 |
| valve_position | percent | 1.0028 | 0.9872 | 1.0060 |
| outlet_flow | m3/h | 4.9981 | 4.9322 | 5.0214 |
| tank_level | m | 0.0507 | 0.0490 | 0.0507 |

For comparison, the raw standard deviation of seed 42 before removing the profile is 10.6604 (pump_command), 28.9464 (pump_flow), 0.3236 (pump_pressure), 7.1639 (valve_position), 28.8150 (outlet_flow) and 0.3575 (tank_level). INFERRED consistency check, not a result: the follower values are close to what the profile implies, for example pump_flow: sqrt((2.7 x 1.0)^2 + 3.0^2) = 4.04 against 4.03 measured.

## Look-back check (READ from `profiles/water_treatment/profile.yaml`; done before any detector exists)

Criteria sections 1 and 2 require: longest look-back <= incident-free margin <= gap.

| Quantity | Value | Source |
|---|---|---|
| Longest B1 look-back (largest W candidate) | 48 h | approved by Huy on 2026-11-25 (Q10) |
| Incident-free margin at a split boundary | 48 h (`boundary_margin_hours`) | READ |
| Gap between splits | 168 h (`split_gap_days` 7) | READ |
| Minimum gap between incidents | 24 h (`min_gap_hours`) | READ |

48 <= 48 <= 168 holds. The time-of-day profile and the standardisation constants are estimated on the training split only and add no look-back. A test in M3b keeps the largest W at most `boundary_margin_hours` for every profile, so a later change of W or of the margin fails loudly.

## Must (in this order)

### M3a (28-29 Nov): injection only

1. **Injection primitives in core**, with neutral names: `slope`, `hold`, `step_offset`, `scale_relation`, `replay`, `command_override`. (The name `ramp` is not used: it is a plant term in `profiles/engine_test_cell/plant_terms.txt`, so the plant-term test would fail on it; checked, RAN.) A profile maps each incident class to a primitive, a target set and parameters.
   - Order of application: command, followers, physical faults, measurement noise, reported-layer changes. So a `command_override` is applied to the independent source before its followers are computed and the followers respond; physical faults change the physical layer; the measurement-noise streams are not touched; drift, stuck, offset and replay change the reported layer last.
   - Injection is a post-processing of the generated arrays: it never changes the random streams, so nothing outside an incident window changes.
   - Each incident has its own seed, derived from the run seed, the class and the start time. Magnitude, target and sign are not affected by other incidents. For `replay` the order of preference of the lags is fixed by the incident alone, but another incident that overlaps a candidate source stretch rules that lag out.
   - An option turns injection off; with it off the output equals the output before M3.
2. **Profile 1 targets and a parameter table**, committed in the profile. One chart per class, with the incident window marked, for Huy to judge visibility. No detector exists at this point. Changing `profile.yaml` changes its hash, so the next demo adds a run (M2 decision 9).
3. **Tests**, neutral names:
   - clean twin: outside incident windows the stored readings equal the no-injection run of the same seed;
   - injection off reproduces the `profile1-done` regression reference (the two hashes in `docs/specs/m2.md`, same machine only, see its Known limits);
   - the same seed gives the same result, a different seed a different one;
   - the labels are unchanged by injection;
   - no plant terms in core (the existing plant-term test);
   - replay lag feasibility: for seeds 42-46, every scheduled incident of profile 1 has at least one valid replay lag within the chosen upper bound (the copied stretch lies inside the split, overlaps no incident window, and the lag is not a multiple of 24 h). If the test fails for some seed, it is reported with the seed and the incident, and the bound is not changed silently: Huy decides, before the tag, and the change is recorded.
4. **Tag `m3-injection-frozen`**, after Huy approves the ranges at the chart review and the parameters are committed, before any detector code exists.

If time on 28-29 Nov: M3b item 5 (the evaluation code).

### M3b (16-18 Dec, after the exams)

5. **Evaluation code** per criteria sections 5-7: alarm merging with G = 3 sampling intervals, overlap matching, recall (overall and per class, with counts), detection delay (median and 90th percentile, number undetected), false alarms per day, event precision, point-level precision, recall and F1, bootstrap over incidents with at least 1,000 resamples and a fixed seed, the "beats" rule, and the budgets 0.25, 0.5, 1 and 2 false alarms per day (1 is B, P3). Tested on hand-computed synthetic alarms before any detector exists.
6. **R0 and B1**, with a test that a detector runs without the incident-label table and a static check that detector modules never reference it.
   - R0: the fixed rule from the profile's nominal ranges (criteria section 3).
   - B1 (exact form, fixed here): for each sensor, residual r(t) = value minus the training-split mean of its time-of-day slot. For a window W (whole sampling intervals, the window includes t): level L(t) = mean of r over W; dispersion D(t) = standard deviation of r over W. Each statistic is standardised with its own mean and standard deviation over the training split (windows lying entirely inside the training split): z = (statistic - mean) / std. The score is the largest absolute z over all sensors and both charts. A timestamp raises an alert when the score exceeds k. The score is undefined until the window is full and never reaches into another split.
   - Configurations: W from the candidate list, k chosen on validation by criteria section 4 for each W; W is chosen by the same rule. Ties go to the larger k (criteria section 4), then to the shorter W (approved by Huy on 2026-11-25).
7. **Validation sweep and one frozen test run.** Every configuration evaluated on validation is logged in a committed file. Thresholds are then frozen, and the test split is evaluated once per frozen configuration (B and the three sensitivity budgets, primary seed only). For each of the budgets 0.25, 0.5, 1 and 2, W and k are chosen on validation by the same rule (criteria section 4); each budget is its own frozen configuration. Seeds 43-46 are repeats with thresholds recalibrated on each validation split (mean and standard deviation, never changing the verdict). Results are written with negative results as prominent as positive ones, in the README results section including R0 and with confidence intervals. Then the tag `m3-done`.

If M3b is not done on 18 Dec, it is reported as a slip; M4 shrinks by the unfinished amount and nothing is dropped silently. Huy decides what is cut.

## Class mapping and magnitudes (approved by Huy on 2026-11-25; frozen by the tag `m3-injection-frozen`)

Profile 1 classes and patterns are in `docs/problem-brief.md` section 4 (READ). Targets and parameters below were chosen from those descriptions and reviewed on charts; none is tuned against a detector, because no detector exists. m is drawn per incident, uniformly within the range, with the incident's seed. Unit: multiples of sigma_s of the target sensor (measured above). A `scale_relation` replaces the physical value v of a follower by offset + s x (v - offset), where offset is the `follows.offset` of the target and s = 1 - q (shortfall) or 1 + q; q > 0 is set so that the mean absolute deviation over the incident window equals m x sigma_s, that is q = m x sigma_s / mean(|v - offset|) over the window. A worked example follows the table.

| Class | Type | Primitive and layer | Target set | Magnitude m (option C' below) |
|---|---|---|---|---|
| sensor_drift | fault | `slope`, reported: moves linearly from 0 to the peak at the end of the window | one of the six sensors | peak m x sigma_s, m in [3, 6] |
| stuck_sensor | fault | `hold`, reported: repeats the first value of the window | one of the six sensors | none |
| weak_pump | fault | `scale_relation`, physical: shortfall against what the pump command implies | pump_flow or pump_pressure | m in [3, 6], direction: shortfall |
| valve_fault | fault | `scale_relation`, physical: outlet flow no longer tracks the valve position | outlet_flow | m in [3, 6], sign random |
| manipulated_readings | attack | `step_offset`, reported only: the value no longer agrees with its related sensors | one sensor that has a relation partner (pump_command, pump_flow, pump_pressure, valve_position, outlet_flow) | m in [3, 6], sign random |
| manipulated_commands | attack | `command_override`, physical: applied before the followers, which respond | pump_command or valve_position | m in [3, 6], sign random |
| replayed_data | attack | `replay`, reported: an earlier stretch is repeated | all six sensors, with the same lag | none; lag rule in Q4 |

### Worked example: `scale_relation` on profile 1 (RAN, 2026-11-21, simulated data)

Case: `weak_pump` on `pump_flow`, physical layer (the shortfall direction), seed 42. The incident is the first `weak_pump` incident of the stored schedule of seed 42 (from `generate_schedule`): validation split, 2026-01-26 12:15 to 18:15 (end exclusive), 24 samples, 6 hours. `pump_flow` follows `pump_command` with `offset` 11.0 and `gain` 2.7 (READ from the profile). sigma_s of `pump_flow` on this run's training split is 4.0268 m3/h (the same method and value as the seed 42 row above). Over the window the mean physical `pump_command` is 60.662 percent, the mean physical `pump_flow` is 174.787 m3/h (= 11.0 + 2.7 x 60.662) and the mean of |v - offset| is 163.787 m3/h.

| m | Target mean absolute deviation (m x sigma_s, m3/h) | q | s = 1 - q | Gain after, 2.7 x s | Mean absolute deviation after (check) | Largest absolute deviation in the window |
|---|---|---|---|---|---|---|
| 2 | 8.0536 | 0.04917 | 0.95083 | 2.5672 | 8.0536 | 8.9207 |
| 3 | 12.0804 | 0.07376 | 0.92624 | 2.5009 | 12.0804 | 13.3811 |
| 6 | 24.1609 | 0.14751 | 0.85249 | 2.3017 | 24.1609 | 26.7622 |

Reading it for m = 3: during the 6 hours the pump flow is about 6.9% below what the command implies (mean 174.787 down by about 12.08 m3/h to about 162.7), because the part above the offset is scaled by 0.926 (q = 7.4% of that part); the relation's gain behaves like 2.50 instead of 2.70. The check column equals the target by construction, so it shows the arithmetic, not an independent test. The deviation is applied to the physical layer, before measurement noise (the noise of `pump_flow` has standard deviation 3.0, READ), and sigma_s is measured on the reported layer, which includes that noise. The numbers depend on the window of this one incident; another incident gives another q for the same m. m = 2 is outside the approved range [3, 6]; its row is kept as an arithmetic illustration only.

## Known limits

- B1 is per sensor, so classes defined by cross-sensor relations (weak_pump, valve_fault, manipulated_readings) may be missed. No result is predicted here.
- The simulator and the detectors are written by the same person. The dispersion chart is the standard pairing for a level chart, but it is still the author's choice.
- weak_pump affects one sensor, as in the problem brief, so on the same sensor it differs from manipulated_readings mainly in shape (proportional shortfall versus a fixed step); a later fault-versus-attack diagnosis may rest on that shape alone.
- A time-of-day-aligned replay (a lag that is a multiple of 24 h) is the hardest case and is not measured.
- Injection generality is not tested by profile 2 (Q5).
- G = 3 intervals is 15 minutes on profile 2 and 45 minutes on profile 1, if profile 2 is ever evaluated (criteria section 9).
- The M2 index result was measured on PostgreSQL 18.6 only; re-measure it if the major version changes (for example in the M7 CI).
- pytest and ruff are not pinned yet; pin them before M7.
- The "same seed, identical readings" claim holds on one machine and one set of library versions (`docs/specs/m2.md`, Known limits).
- The magnitude range [3, 6] was chosen at the chart review, before any detector ran. Incidents weaker than 3 sigma_s are not in the evaluation, so nothing is claimed about them. The author's judgement that incidents near 2 sigma_s would be undetectable for any simple per-sensor detector is an inference, not a measurement.
- slope (sensor_drift) is defined by its peak m x sigma_s at the end of the window, starting from 0, so its average deviation over the window is half the peak, 1.5 to 3 sigma_s for m in [3, 6]. The step classes deviate by about m sigma_s from the first sample. At the same m, sensor_drift is therefore the hardest class; this was seen on the review charts and is not a measurement of any detector.

## Chart review (2026-11-25)

The options and reasons are kept for the record, with the option Huy chose on 2026-11-25. The three injection choices (items 1, 3 and 4) are frozen by the tag `m3-injection-frozen`; the W list (item 2) was approved the same day and is fixed before any validation run. None of the options was measured against a detector.

1. **Magnitude ranges. Chosen: C', [3, 6]** (approved by Huy on 2026-11-25; frozen by the tag `m3-injection-frozen`).

   | Option | Range of m | Reason | Cost |
   |---|---|---|---|
   | A | [4, 8] for every class | Clearly visible incidents; easy to judge on a chart | May be too easy: every method could reach full recall, which separates nothing |
   | B (recommended) | [2, 6] for every class | One common range, so one knob; marginal and obvious incidents both occur | The weak end (2 x sigma_s) may be invisible on a chart; Huy judges this at the review |
   | C | [1.5, 8], or a different range per class | Widest spread of difficulty | More knobs to fix before the tag; harder to explain |
   | **C' (chosen)** | [3, 6] for every class with a magnitude | At m near 2 the charts showed a deviation within the noise of the signal, visible only against the clean twin | Incidents weaker than 3 sigma_s are not evaluated |

2. **Window W candidates** for B1 (each at most 48 h). **Chosen: A** (approved by Huy on 2026-11-25). Incident durations are 2-8 h (READ, `duration_hours`).

   | Option | W | Reason |
   |---|---|---|
   | A (recommended) | 2 h, 8 h, 24 h, 48 h | Two values near the incident length, one day, and the cap at the margin; four values keep the visible tuning small |
   | B | 4 h, 12 h, 48 h | Fewer values, fewer configurations to log |
   | C | one value, 24 h | No tuning of W at all; loses the check of whether the window length matters |

3. **Replay lag upper bound** (lower bound 25 h). **Chosen: B, 168 h** (approved by Huy on 2026-11-25; frozen by the tag `m3-injection-frozen`). A lag must give a copied stretch that lies inside the split and overlaps no incident window; the injection fails loudly if none exists.

   | Option | Upper bound | Reason |
   |---|---|---|
   | A | 48 h | Equal to the margin, so the stretch always lies after the split start; fewer candidate stretches, since incidents are only 24 h apart at the least |
   | B (recommended) | 168 h | Equal to the gap; many candidate stretches (target to be checked by a test, M3a item 3) |
   | C | none, limited by the split only | Most freedom; lags of weeks make the copied stretch far from the incident's context |

   With every option, lags that are multiples of 24 h are excluded, so the known limit about aligned replay stays true.

4. **Sign rule** of `step_offset`, `slope`, `scale_relation` and `command_override`. **Chosen: B** (approved by Huy on 2026-11-25; frozen by the tag `m3-injection-frozen`): fixed direction where the class has one, random otherwise (so `sensor_drift` and `valve_fault` are random too).

   | Option | Rule | Reason |
   |---|---|---|
   | A | Random sign for every incident, from the incident's seed | Simple; no one-sided bias |
   | B (recommended) | Fixed direction where the class has one (weak_pump: shortfall), random sign for the attacks | A weak pump is a shortfall by definition; an attacker can go either way |
   | C | Always positive | Simplest; hides whether a one-sided rule would work |
