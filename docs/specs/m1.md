# M1 spec: simulator to database to one chart

Status: confirmed by Huy on 2026-11-08. All data is simulated. No real plant is modelled, and every numeric value in a profile is invented for the simulation.

## Decisions (Huy, 2026-11-08)

| Topic | Decision |
|---|---|
| Incident scope | Generate and validate the labelled incident schedule. Do not inject incidents into signals. Injection moves to the start of M3. |
| Sampling interval | 15 minutes |
| YAML library | `ruamel.yaml` |
| Chart | `matplotlib`, one PNG |
| Q1: coupling form | Linear `follows`: offset + gain x the source's value at the same timestamp |
| Q2: relations in profile 1 | Three: `pump_flow` and `pump_pressure` follow `pump_command`; `outlet_flow` follows `valve_position` |
| Q3: signal layers | Two: physical and reported. Only reported values go to the database |
| Q4: gap between splits | Real, 7 days, inserted between the splits, not stored |
| Q5: daily phase | Separate per independent source: 0, 8 and 16 h |

## Also confirmed (Huy, 2026-11-08)

1. Further dependencies: `numpy` (signals) and `psycopg[binary]` (database). Both resolve to wheels on Python 3.15 in a pip dry run. No `pandas` in M1.
2. No incidents in the training split. P2 only sets minimums for validation and test, and criteria section 2 says detectors never read labels, so a clean training split fits. Limit: real training data would rarely be this clean. This is recorded in criteria section 12.
3. No database password in M1. The database uses trust authentication, bound to `127.0.0.1` only, so no secret exists to commit or read. API authentication stays in M6 (ADR 0005).

## Must

1. Plant-profile YAML structure: `profiles/water_treatment/profile.yaml`.
2. A minimal `compose.yaml` that starts only PostgreSQL (ADR 0001), with the image version pinned.
3. A minimal `db/schema.sql` with generic tables only: `profiles`, `sensors`, `readings`, `context_readings`, `incident_labels`. M2 adds indexes, data-quality checks and the migration decision.
4. A seeded simulator in `src/plantmon/sim/`, driven only by the profile: each independent signal is base + daily sine + AR(1) noise (followers: Must item 12). No plant terms in the code.
5. The optional context channel (ADR 0006): a profile may define states and a per-state offset. The profile `water_treatment` defines none, so `context_readings` stays empty. A test covers both cases with neutral names (`alpha`, `beta`).
6. An incident schedule generated from the seed and written to `incident_labels`, plus a validator that fails on any of:
   - fewer than the minimum incidents per class in validation or test;
   - anomalous share above the maximum in any split;
   - any incident in the training split;
   - any overlap between incidents, or a gap shorter than `min_gap_hours` (24), so one alarm cannot span two incidents;
   - any incident crossing a split boundary or inside the boundary margin.
7. Ingestion into PostgreSQL with `COPY`.
8. One command, `python -m plantmon demo --profile water_treatment`: starts the database, simulates, ingests, validates and writes `data/generated/chart.png`. The chart is labelled as simulated.
9. Import smoke test in the project venv for every chosen library, then pin exact versions in `pyproject.toml`.
10. Feasibility report for P2 and the sampling interval: measured counts and anomalous share per split, measured row count and run time. If P2 is infeasible, the fix is recorded before the tag (criteria section 1.4).
11. Create the tag `eval-criteria-v1`, only after Huy confirms the frozen values, before any detector runs on validation or test data.
12. Generic cross-sensor coupling, driven only by the profile: an optional `follows` block {source, gain, offset} and an optional `measurement_noise_std` per sensor. The simulation result exposes the physical and the reported layer; no injection code. The profile loader rejects an unknown source, a self reference, a cycle (chains are allowed), a non-finite gain or offset, a context channel as source, and `follows` combined with a signal block. Tests use a neutral synthetic profile (`a`, `b`, `c`): exact follower values without noise, reported differs from physical with noise, a chain, every rejection, same and different seeds, and an independent sensor that does not change when a follower is added. A test also keeps every repo profile at `min_gap_hours` >= 24 and `boundary_margin_hours` >= 48.
13. A real gap between splits (`split_gap_days`, 7 for profile 1) that is generated over the continuous timeline and never stored, and an optional `daily_phase_hours` per independent signal (0, 8 and 16 h in profile 1). Tests cover gap absence, both gap lengths, measured split lengths, phase 0, the phase shift, a non-finite phase, a follower inheriting its source's phase, and schedule validity on the new bounds. The criteria chain is look-back <= margin <= gap; a test keeps margin <= gap for every profile.

## If time

- Seasonality in the simulator.
- Inject drift, stuck sensor and replayed data.

## Not in M1

Detectors, dashboard, API layer, audit log, profile 2, indexes beyond primary keys, incident injection (except the "if time" item above), lag in `follows`, an integrator relation (see `docs/backlog.md`).

## Done when

- From a clean clone, `python -m plantmon demo --profile water_treatment` produces the chart with Docker running.
- The same seed gives identical readings and schedule; a different seed does not (tested).
- The row count in `readings` equals sensors x samples (tested at small size, measured at full size).
- The validator fails on a broken schedule for each rule above (tested).
- `git grep` finds no plant-specific terms in `src/plantmon/`, `db/` or the core tests.
- pytest and ruff pass, with raw output pasted.

No performance claim is made until it is measured.

## Measured feasibility (2026-11-08, simulated data, one local machine)

`python -m plantmon demo --profile water_treatment --seed <seed>`: 15-minute sampling, train 365 days (2025-01-01 to 2026-01-01, exclusive) with 35,040 samples per sensor, validation 90 days (2026-01-08 to 2026-04-08) with 8,640, test 91 days (2026-04-15 to 2026-07-15) with 8,736. That is 546 stored days, 52,416 samples per sensor, 6 sensors and 314,496 readings; no reading is stored inside the two 7-day gaps. 35 incidents in each of validation and test, 5 per class, none in train.

| Seed | Validation anomalous share | Test anomalous share | Run time (s) |
|---|---|---|---|
| 42 | 0.0799 | 0.0861 | 5.8 |
| 43 | 0.0840 | 0.0781 | 4.2 |
| 44 | 0.0755 | 0.0888 | 4.1 |
| 45 | 0.0711 | 0.0875 | 4.0 |
| 46 | 0.0773 | 0.0766 | 4.2 |

Every share is below the 0.10 limit in P2, so P2 and the sampling interval are feasible for these seeds and this profile. Run times include a database that was already running.

## Known limits of the M1 signals

- Each independent source has its own daily phase, but unrelated sensors still correlate through their daily cycles: in the training split of seed 42, tank_level vs pump_command is -0.4919, tank_level vs valve_position is -0.4898 and pump_command vs valve_position is -0.4942, against 0.9947 (pump_flow vs pump_command), 0.9879 (pump_pressure vs pump_command) and 0.9946 (outlet_flow vs valve_position) for the coupled pairs. A correlation near zero is therefore not what separates unrelated sensors here.
- No reading leaves its nominal range in the training split (measured for seed 42 with the coupling, gaps and phases), so before injection the naive reference R0 would raise no alert there.

## Known consequence

Moving injection to M3 means the M2 generality test does not exercise injection code. Any core change that injection needs later is not caught by the diff between `profile1-done` and `profile2-done`, so M3 must report those changes separately.

- M2: data-quality checks must treat the two split gaps as expected holes (derive them from the profile's split bounds) and must test real missing data by injecting it separately.
- M3: the spec must state the longest look-back of every detector and show it is at most the 48-hour margin before any detector runs; injection parameters are committed before detectors run (criteria section 1, item 6).
